# 11 · 最佳实践与常见坑

> 上一篇：[hooks 概览](10-hooks概览.md) · 返回：[课程大纲](00-课程大纲.md)

## 1. 推荐习惯

1. **小步提交**：一个逻辑点一笔；易 revert、易 review。
2. **主分支保护**：PR + 审查 + CI；本地不直接推 `main`（若团队允许直推，仍应 pull 再 push）。
3. **拉取策略统一**：全员 merge 或全员 rebase，写进 README。
4. **密钥不入库**：`.env`、私钥、token 进 `.gitignore`；已误提交立刻轮换密钥并用历史清理工具（需团队流程）。
5. **说明写清意图**：为什么改，不单是改了什么。
6. **发版打附注 tag**，CI 以 tag 为准出包。
7. **长任务用 worktree 或 WIP 分支**，少堆长期 stash。

## 2. 常见坑

### 2.1 在错误的分支上改完了

```bash
git stash push -u -m "wip"
git switch correct-branch
git stash pop
# 或：错分支上先 commit，再 cherry-pick 到正确分支后 reset 错分支
```

### 2.2 `commit` 后才发现漏文件 / 写错说明（未 push）

```bash
git add forgotten.ts
git commit --amend --no-edit
# 改说明：git commit --amend
```

已 push：优先后续补提交；强推仅限个人分支且团队允许。

### 2.3 误 `reset --hard`

立刻 `git reflog`，找到 hard 之前的 `HEAD@{n}`，`git reset --hard HEAD@{n}` 或建恢复分支。

### 2.4 把 `node_modules` / 构建物提交进去

```bash
echo "node_modules/" >> .gitignore
git rm -r --cached node_modules
git commit -m "chore: stop tracking node_modules"
```

### 2.5 线历史被 rebase 后 pull 冲突一团

个人分支：`git fetch` 后 `git reset --hard origin/feature/x`（确认无独有本地提交）。  
或：`git pull --rebase`。不要盲目 merge 出双倍提交除非你懂。

### 2.6 忘记 `-u`，stash 后新文件还在

养成 `git status -sb`；需要时 `stash push -u`。

### 2.7 Submodule「空目录」

克隆后要 `git submodule update --init --recursive`，见 [Submodule 指南](Git%20Submodule%20使用指南.md)。

### 2.8 行尾与文件名大小写

Windows/macOS 忽略大小写可导致「改名不生效」；`core.ignorecase`、`.gitattributes` 的 `eol` 按团队统一。

## 3. 速查：别在这些场合 force push

- `main` / `release/*` 等保护分支
- 已有同事基于其上继续开发的共享功能分支（除非协调好）
- 已公开发布的 tag 指向的历史

## 5. 系列收束

从三区模型 → 命令 → 分支整合 → 协作与自救 → 标签与钩子 → 习惯，日常 90% 场景已覆盖。遇到问题时：

1. `git status -sb`
2. `git log --graph --oneline --decorate -n 20`
3. 需要自救时再 `git reflog`
