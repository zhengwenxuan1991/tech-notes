# Geohash

Geohash 是一种地理空间索引技术，将二维经纬度坐标 $(lat, lon)$ 编码为一维字符串。本质是**空间填充曲线**在计算机科学中的应用。

> 算法原理详见 [[Geohash 算法原理]]

## 1. 精度与长度关系

每增加 1 个字符（5 位二进制），面积缩小到 $\frac{1}{32}$（宽高分别缩小约 4~8 倍）。

> Geohash 的灵魂：**前缀越长，范围越小，且前缀相同的点在地理位置上通常（但不绝对）靠近**。

### 完整精度参考表

Geohash 实际标识一个矩形单元格，每增加一个字符将当前格子细分为 32 个子格子。

> **注意**：宽度（经度方向）随纬度升高而减小，在极地处趋近于 0。下表列的是赤道处的最大值（≤），高度（纬度方向）全球一致。

| 长度 | 宽度（≤）  | 高度       | 典型用途          |
| ---- | ---------- | ---------- | ----------------- |
| 1    | 5,000 km   | 5,000 km   | 洲级              |
| 2    | 1,250 km   | 625 km     | 国家级            |
| 3    | 156 km     | 156 km     | 城市级            |
| 4    | 39.1 km    | 19.5 km    | 区县级            |
| 5    | 4.89 km    | 4.89 km    | **商圈级**        |
| 6    | 1.22 km    | 0.61 km    | **街道级**        |
| 7    | 153 m      | 153 m      | **围栏/轨迹**     |
| 8    | 38.2 m     | 19.1 m     | 园区/停车场       |
| 9    | 4.77 m     | 4.77 m     | 车位级            |
| 10   | 1.19 m     | 0.596 m    | 超高精度          |
| 11   | 149 mm     | 149 mm     | 测绘级            |
| 12   | 37.2 mm    | 18.6 mm    | 极限精度          |

### 为什么是长方形而非正方形？

两个原因：
1. 经度范围 $[-180, 180]$ 是纬度 $[-90, 90]$ 的两倍，天然不等比
2. 每个字符 5 位无法均分给经纬度（奇数长度时 3 位经度、2 位纬度），导致格子呈长方形

## 2. Z-阶曲线 (Z-Order Curve)

Geohash 基于 Z-阶曲线，将二维平面映射到一维：

| 坐标   | 编码  |
| ------ | ----- |
| (0, 0) | `00`  |
| (0, 1) | `01`  |
| (1, 0) | `10`  |
| (1, 1) | `11`  |

按编码顺序连线形成 "Z" 字形，递归细分后每个方格内部又生成更小的 "Z"。

**核心特性**：
- **局部性 (Locality)**：编码数值接近的点，地理位置通常也接近
- **前缀匹配**：公共前缀即地理邻近 → `SELECT * FROM points WHERE geohash LIKE 'wx4g0%'`

## 3. 边界突变问题

Z 曲线的原生缺陷：在 "Z" 字转折处，物理位置紧邻的两个点编码可能完全不同。

> 线左边 `0111`，线右边 `1000`，物理距离 1 米但无任何公共前缀。

**解决方案**：查询"附近"时，必须同时计算**周围 8 个邻居方块**。

## 4. 车联网场景精度选型

> Geohash 只是**空间索引精度**，不是真实空间精度。精确判断仍需 `ST_CONTAINS`，Geohash 的目标是**减少 ST_CONTAINS 次数**。

### 5~8 级适用场景对比

| 级别     | 大小    | 适合场景                         | 注意事项                      |
| -------- | ------- | -------------------------------- | ----------------------------- |
| geohash5 | 约 5km  | 城市热力图、区域统计、粗粒度分析 | 误差较大                      |
| geohash6 | 约 1km  | 实时大盘、行政区统计、城市级轨迹 | 网格偏大，INTERSECT 多        |
| **geohash7** | **约 150m** | **车辆围栏统计（推荐）**         | **网格适中、FULL_INSIDE 比例高、ST_CONTAINS 次数明显下降** |
| geohash8 | 约 38m  | 停车场、小园区、精细轨迹         | 围栏 Geohash 数量爆炸、JOIN 膨胀、生成成本高 |

### 为什么 geohash7 是最佳平衡？

- 网格不算太大 → FULL_INSIDE 比例较高
- Geohash 数量还能接受 → JOIN 数据量可控
- ST_CONTAINS 次数明显下降 → 精判开销低

### Geohash 大小与围栏复杂度的权衡

| 调整方向 | 收益                     | 代价                     |
| -------- | ------------------------ | ------------------------ |
| 精度提高 | 边界误差减小             | INTERSECT 数量暴增、mapping 表膨胀 |
| 精度降低 | Geohash 数量少、JOIN 快 | 边界锯齿更多、误差变大   |

### 实际推荐

| 场景         | 推荐精度     |
| ------------ | ------------ |
| 默认（围栏/轨迹/道路/园区） | **geohash7** |
| 大区域统计   | geohash6     |
| 小围栏/停车场 | geohash8     |

## 5. 工程实践

### 数据库应用

- **Redis**：`GEOADD` / `GEORADIUS`（底层基于 Geohash）
- **MongoDB / Elasticsearch**：配置地理位置索引
- **SQL**：`WHERE geohash LIKE 'prefix%'` 实现前缀匹配
- **Doris**：Geohash 前缀粗筛 + `ST_CONTAINS` 精判（两阶段过滤）

### 长度选择策略

| 考量维度 | 建议                             |
| -------- | -------------------------------- |
| 查询性能 | 越短索引开销越小                 |
| 隐私保护 | 社交场景用 5-6 位，避免精确定位  |
| 缓存命中 | 越短地理块越大，Redis 利用率越高 |

## 6. 替代方案对比

| 方案            | 曲线类型     | 优势                   | 适用场景          |
| --------------- | ------------ | ---------------------- | ----------------- |
| **Geohash**     | Z-阶曲线     | 简单、前缀查询方便、SQL 友好 | 附近的人、外卖配送、Doris/ES |
| **S2 (Google)** | 希尔伯特曲线 | 大规模计算更均衡       | Google Maps       |
| **H3 (Uber)**   | 六边形分级   | 覆盖均匀、距离衰减好   | 打车匹配          |

Geohash 至今大量使用的原因：**字符串天然支持前缀搜索 + SQL 友好 + 实现极简**，适合 Doris / ES / MySQL 直接用 LIKE 查询。
