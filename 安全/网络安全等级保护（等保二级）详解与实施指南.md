# 网络安全等级保护（等保二级）详解与实施指南

## 一、概述

**网络安全等级保护第二级**（简称**等保二级**，保护级别为**指导保护级**）是国内非涉密信息系统里最常见的一档。一个普通 Web 平台定在这一级，要落实身份鉴别、访问控制、安全审计、边界访问控制、漏洞与恶意代码防范、重要数据的传输保护和备份，以及一套能执行的安全管理制度。

> [!warning] 不要把「等保 2.0」和「等保二级」当成一件事
> **等保 2.0** 是 2019 年这套标准的代际名称，核心标准是 GB/T 22239-2019，用来替换 2008 年的等保 1.0。**等保二级**是五个保护等级里的第二级。一套标准里同时存在第一级到第四级的要求，第五级另有专控安排。

> [!important] 依据
> 1. 《中华人民共和国网络安全法》第二十一条：国家实行网络安全等级保护制度。网络运营者应履行安全保护义务，并按规定留存相关网络日志不少于 6 个月。
> 2. GB/T 22239-2019《信息安全技术 网络安全等级保护基本要求》：各级「应」条款的直接依据。
> 3. GB/T 22240-2020《信息安全技术 网络安全等级保护定级指南》：定级矩阵。
> 4. GB/T 28448-2019《信息安全技术 网络安全等级保护测评要求》：测评怎么查、怎么判。

正式建设和测评以标准全文、测评要求，以及备案地公安机关网安部门的口径为准。本文是 Web 平台第二级安全通用要求的实施基线，不是测评打分表。

三级的控制项、集中管控和每年测评要求见 [[安全/网络安全等级保护（等保三级）详解与实施指南|等保三级详解与实施指南]]。

## 二、五个等级与二级的位置

定级看系统一旦被破坏，会伤害谁、伤害到什么程度，不看公司规模，也不看「是不是一个网站」。GB/T 22240-2020 用「受侵害客体 × 侵害程度」取较高者：

| 受侵害客体 | 一般损害 | 严重损害 | 特别严重损害 |
| --- | --- | --- | --- |
| 公民、法人和其他组织的合法权益 | 第一级 | 第二级 | 第二级 |
| 社会秩序、公共利益 | 第二级 | 第三级 | 第四级 |
| 国家安全 | 第三级 | 第四级 | 第五级 |

| 等级 | 保护级别 | 定到这一级的典型情形 | 监管与测评 |
| --- | --- | --- | --- |
| 第一级 | 自主保护级 | 只一般损害公民、法人合法权益 | 自主保护。二级及以上才强制备案 |
| **第二级** | **指导保护级** | **严重损害公民、法人合法权益，或一般损害社会秩序和公共利益，不损害国家安全** | **向公安机关备案。测评为定期开展，很多地方按至少每两年一次掌握** |
| 第三级 | 监督保护级 | 严重损害社会秩序和公共利益，或一般损害国家安全 | 备案，且每年至少测评一次 |
| 第四级 | 强制保护级 | 特别严重损害社会秩序和公共利益，或严重损害国家安全 | 每半年至少测评一次，强制监督 |
| 第五级 | 专控保护级 | 特别严重损害国家安全 | 国家指定部门专控 |

《信息安全等级保护管理办法》（公通字〔2007〕43 号）写明第三级应当每年至少测评一次。第二级没有写死「每年」。各地对备案证明有效期、复测间隔的掌握不一致，以备案地网安部门为准。

## 三、什么系统一般定二级

定级对象是**独立运行、单独承载业务的信息系统**，不是整家公司。官网、业务平台、OA 应分开定级。

常见可以论证为二级的系统：

- 企业官网、产品介绍站、影响范围限于本单位的内部 OA、HR、一般协同系统。
- 用户规模有限、不掌握大量敏感个人信息、被破坏后主要损害本单位或用户个体权益的业务系统。

下面这类系统，行业主管部门经常要求按三级建设，不能因为「只是一个 Web」就定成二级：

- 涉及大量个人信息、交易支付、政务服务、医疗、教育招生的核心系统。
- 一旦中断或数据泄露，会严重影响社会秩序或公共利益的平台。

二级及以上定级、级别变更和系统重大变化，需要组织专家评审后再向公安机关备案。

## 四、要求怎么读

GB/T 22239-2019 把每一级拆成**安全通用要求**，云计算、移动互联、物联网、工业控制另加**安全扩展要求**。通用要求有 10 个层面：

- 技术：安全物理环境、安全通信网络、安全区域边界、安全计算环境、安全管理中心。
- 管理：安全管理制度、安全管理机构、安全管理人员、安全建设管理、安全运维管理。

标准里的「应」是强制项，「可」是可选。二级的可信验证（可信计算）是「可」，不作为通过条件。

部署在云上、带 App，或接入物联网设备时，不能只用下面的通用要求，还要对照对应扩展要求，并在合同和测评材料里写清云平台与云租户的责任边界。

## 五、Web 平台的第二级技术要求

### 1. 安全计算环境

对象包括操作系统、数据库、中间件、Web 应用和其中的重要数据。这是研发最直接对应的一层。

**身份鉴别**

- 登录用户有身份标识和鉴别，标识唯一，不使用共享账号。
- 鉴别信息有复杂度要求，并定期更换。国标没有写死「8 位、三类字符、90 天、失败 5 次锁定」。这些是测评里常见的判定口径，以本单位口令策略和测评机构口径为准。
- 具备登录失败处理：结束会话、限制非法登录次数、登录连接超时自动退出。
- 远程管理（SSH、运维后台、数据库管理）采取措施，防止鉴别信息在网络上被窃听。SSH、HTTPS、VPN 都算这类措施。

**访问控制**

- 为登录用户分配账户和权限。
- 重命名或删除默认账户，修改默认口令。
- 及时删除或停用多余的、过期的账户。
- 管理用户只授予所需的最小权限，管理职责分离。

**安全审计**

- 启用审计，覆盖每个用户，审计重要用户行为和重要安全事件。
- 记录包含日期和时间、用户、事件类型、事件是否成功，以及其他相关信息。
- 保护审计记录，定期备份，避免被未预期地删除、修改或覆盖。
- 日志留存不少于 6 个月，这是《网络安全法》第二十一条对网络运营者的义务，不因定为二级而降低。

**入侵防范**

- 最小安装，只装需要的组件和应用程序。
- 关闭不需要的系统服务、默认共享和高危端口。
- 通过接入方式或网络地址范围，限制可以远程管理的终端。
- 对人机接口和通信接口的输入做有效性检验。SQL 注入、跨站脚本、非法上传、越权参数都落在这一项。
- 能发现已知漏洞，充分测试评估后及时修补。

**恶意代码防范**

- 安装防恶意代码软件，或配置具有同等能力的软件，并定期升级恶意代码库。主机防护、云主机安全代理属于常见落地。

**数据完整性与保密性**

- 采用校验技术保证重要数据在传输过程中的完整性。
- 采用密码技术保证重要数据在传输过程中的保密性，范围包括鉴别数据、重要业务数据和重要个人信息。对 Web 平台，这意味着登录、后台和承载这些数据的接口走 TLS，不能用明文 HTTP 传口令。
- 用户口令不得明文落库。鉴别信息所在存储空间在释放或重新分配前应完全清除。

**数据备份与恢复**

- 提供重要数据的本地备份与恢复。
- 提供异地备份，利用通信网络把重要数据定时批量传送到备用场地。
- 备份要能恢复。只「有备份任务」而从未做过恢复验证，测评时站不住。

**个人信息保护**

- 只采集和保存业务必需的用户个人信息。
- 禁止未授权访问和非法使用用户个人信息。

### 2. 安全通信网络

- 网络设备处理能力和各段带宽满足业务高峰。
- 划分不同网络区域，并按便于管理和控制的原则分配地址。
- 重要网络区域不部署在边界上，与其他区域之间有可靠的技术隔离。对外服务区、应用区、数据区、管理区分开是常见做法。
- 采用校验技术保证通信过程中数据的完整性。

通信网络这一层，二级只强制传输完整性。通道级保密（例如全流量 IPSec）是第三级才增加的「应」。应用层仍然必须对口令和重要业务数据使用 TLS，依据来自上一节的数据保密性，以及远程管理防窃听。

### 3. 安全区域边界

- 跨越边界的访问和数据流，只通过边界设备提供的受控接口通信。防火墙、云安全组都属于这类接口。
- 按访问控制策略设置规则，默认除允许的通信外全部拒绝。
- 删除多余或无效规则，规则数量最小化。
- 检查源地址、目的地址、源端口、目的端口和协议，据此允许或拒绝。
- 能根据会话状态对数据流做允许或拒绝。
- 在关键网络节点监视网络攻击行为。二级的要求是**监视**；检测并限制从外部或内部发起的攻击，是第三级增强项。
- 在关键网络节点检测和清除恶意代码，并维护防护机制的升级和更新。
- 在网络边界和重要网络节点做安全审计，覆盖每个用户的重要行为和重要安全事件；记录要素、保护与备份要求与计算环境审计一致。

WAF、入侵检测、云上态势感知不是二级条款里的产品名称。它们是满足「输入校验、攻击监视、边界审计」的常见做法。互联网暴露的管理入口若全网放开、存在弱口令或未修复的高危漏洞，测评里通常按高风险处理。

### 4. 安全物理环境

自建机房需要满足：建筑具备防震、防风、防雨能力；顶层或地下室要有加强的防水防潮措施；出入口有专人值守或电子门禁，能控制和记录进入人员；并落实防盗防破坏、防雷、防火、防水防潮、防静电、温湿度、电力供应等第二级条款。

系统部署在公有云或政务云上时，物理环境通常由云平台承担。测评要能拿出云平台相应等级的等保证明，以及双方责任划分。上云本身不等于本系统通过了等保。

### 5. 安全管理中心

第二级有**系统管理**和**审计管理**：

- 对系统管理员做身份鉴别，只允许通过特定命令或操作界面做系统管理，并对这些操作审计。管理范围包括用户身份、资源配置、系统加载和启动、异常处理、数据和设备的备份与恢复。
- 对审计管理员做身份鉴别，只允许通过特定界面做审计操作，并对这些操作审计。审计管理员负责审计记录的分析、存储、管理和查询。

第二级没有第三级那种完整的集中管控：独立安全管理区、设备状态与补丁和审计的集中监控、系统管理员 / 安全管理员 / 审计管理员三权分立且不得兼任。角色怎么拆，见 [[安全/Web系统三权分立与业务权限隔离|Web 系统三权分立与业务权限隔离]]。

## 六、Web 平台的第二级管理要求

管理要求看的是制度文本加上执行记录。只有空文档、没有审批、培训、变更和应急记录，测评判不符合。

**安全管理制度**

- 有总体安全方针和策略，以及账号、访问控制、审计、变更、备份、恶意代码、安全事件等专项制度。
- 制度经过制定、评审和发布，有版本和负责人。

**安全管理机构**

- 有人负责网络安全工作，岗位职责明确。
- 重要操作有授权和审批，审批记录可查。
- 与供应商、云平台、测评机构的协作有联系人和记录。

**安全管理人员**

- 录用时了解身份、背景和专业资格。
- 离岗时交接口令、权限和持有的介质，并停用账号。
- 对相关人员做安全意识教育和培训，并留记录。
- 外部人员物理访问受控区域，或接入受控网络前，先书面申请、批准、专人陪同或开设账户，并登记。

**安全建设管理**

对自行开发的 Web 系统，第二级至少包括：

- 开发环境与实际运行环境物理分开，测试数据和测试结果受控。
- 有软件开发管理制度和代码编写安全规范，开发人员按规范编写。
- 软件交付前检测安装包中可能存在的恶意代码。
- 具备软件设计文档和使用指南，并控制文档的使用。
- 定级、备案、方案设计、产品采购、工程实施、测试验收、系统交付和等级测评有过程记录。外包开发要管住服务商的人员和权限。

**安全运维管理**

- 资产清单覆盖主机、中间件、应用、账号和对外接口。
- 漏洞和补丁有发现、评估、修复和复核记录。
- 配置变更有申请、审批和实施记录。
- 备份按策略执行，并做过恢复验证。
- 有安全事件报告路径和应急预案，预案经过评审。发生事件后有处置记录。

## 七、这些不是二级的强制项

做二级时，方案里经常把三级能力一并写进「必须」。下面这些是第三级及以上才增加或增强的「应」，二级不要当成通过条件，也不要在对客户的承诺里写成二级已覆盖：

| 能力 | 二级 | 三级及以上 |
| --- | --- | --- |
| 身份鉴别 | 唯一账号、口令复杂度与定期更换、失败处理、超时退出、远程管理防窃听 | 另加两种或以上组合鉴别，且其中一种使用密码技术（常见为口令 + 证书、动态口令或生物特征） |
| 访问控制 | 授权、默认账户、过期账户、管理用户最小权限 | 由授权主体配置访问控制策略；粒度到用户或进程对文件、数据库表 |
| 入侵防范 | 最小安装、关高危端口、限制管理终端、输入校验、修补已知漏洞 | 另能检测对重要节点的入侵，严重入侵时报警 |
| 区域边界 | 受控接口、默认拒绝、五元组和会话状态、监视攻击 | 检测并限制外部和内部攻击；按应用协议和应用内容做访问控制 |
| 通信保密 | 应用层对重要数据传输做密码保护 | 通信过程本身采用密码技术保证保密性 |
| 数据存储 | 传输保密；清除残留的鉴别信息 | 重要数据存储保密；另清除残留的敏感数据 |
| 备份 | 本地备份恢复 + 异地定时批量备份 | 另提供重要数据处理系统的热冗余。异地实时备份和异地灾难备份中心是第四级 |
| 管理 | 系统管理、审计管理 | 安全管理岗位独立，集中管控，三权分立且不得兼任 |
| 测评 | 备案后定期测评，常见掌握为至少每两年一次 | 每年至少一次 |

互联网业务即便定二级，弱口令、管理入口对公网全开、高危漏洞未修、没有审计、没有可恢复的备份，仍然是常见高风险项。

## 八、实施顺序

1. **定级。** 划定系统边界，按 GB/T 22240 编写定级报告。二级及以上组织专家评审。
2. **备案。** 向属地公安机关网安部门备案。线上入口一般是全国网络安全等级保护备案系统。定级确认后应尽快备案，各地对时限的要求不同。
3. **差距整改。** 先按本文第十节做自查，再补技术措施和制度记录。先测评、后补材料，周期和费用都会上去。
4. **等级测评。** 委托具备资质的测评机构。结论用于向公安机关提交。
5. **持续保持。** 日志留存、补丁、备份恢复、账号清理、变更和应急记录不断档，并按备案地要求复测。

## 九、和第三级怎么选

只看「有没有用户登录」不够。用定级矩阵里较高的那一格：

- 系统被破坏，主要是本单位或用户个体权益受损，社会影响有限：优先论证二级。
- 系统承载公共服务、大量个人信息或交易，中断或泄露会严重影响社会秩序、公共利益：按三级准备。见 [[安全/网络安全等级保护（等保三级）详解与实施指南|等保三级详解与实施指南]]。
- 定低后在备案审核或客户验收时被要求重定，前面的整改和测评要重做。

## 十、Web 平台自查清单

上线前或备案前，按下面核对。做不到的项先记差距，不要用「云上默认安全」带过。

- [ ] 定级报告写清系统边界、业务和数据、定二级的理由。
- [ ] 已向属地公安机关备案，或已排期备案。
- [ ] 全站对外和管理入口使用 TLS；口令、重要业务数据、个人信息不以明文传输。
- [ ] 账号一人一号；无默认口令、无共享管理账号；过期账号已停用。
- [ ] 口令有复杂度并定期更换；登录失败锁定；会话超时退出。
- [ ] 管理入口限制来源地址，不直接对整个互联网开放。
- [ ] 权限按角色最小化；管理操作和审计职责分开。
- [ ] 登录、权限变更、重要业务操作有审计日志；日志防篡改，留存不少于 6 个月。
- [ ] 输入校验覆盖查询、表单、上传和开放接口；已知高危漏洞已修补或有经批准的例外和期限。
- [ ] 主机有恶意代码防护且库是新的；无用端口和服务已关闭。
- [ ] 安全组或防火墙默认拒绝，只放行业务需要的地址和端口。
- [ ] 网络至少分开对外服务、应用、数据和远程管理。
- [ ] 重要数据有本地备份和异地定时备份，最近一次恢复验证有记录。
- [ ] 只采集业务必需的个人信息，未授权账号不能导出或查看明文。
- [ ] 开发、测试、生产环境分开；有安全编码规范；交付物做过恶意代码检测。
- [ ] 制度、审批、培训、变更、漏洞和应急记录能按时间抽出来。
- [ ] 若在云上：云平台等保证明、责任划分、虚拟机和安全组配置能提供给测评机构。
