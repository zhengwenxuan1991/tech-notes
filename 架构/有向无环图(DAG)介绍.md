# 有向无环图（DAG）

## 定义

**有向无环图**（Directed Acyclic Graph，简称 **DAG**）是一种图结构，满足两个条件：

1. **有向**：每条边都有方向，表示从一个节点指向另一个节点（A → B，不代表 B → A）。
2. **无环**：从任意节点出发，沿着边的方向走，都不可能回到起点，即图中不存在环路。

简单说：DAG 描述的是一组"有先后依赖关系，且不会循环依赖"的事物。

## 与其他图结构的区别

| 图类型 | 是否有方向 | 是否允许环 |
| --- | --- | --- |
| 无向图 | 否 | 允许 |
| 有向图（Digraph） | 是 | 允许 |
| **DAG** | 是 | **不允许** |
| 树（Tree） | 是（一般约定父→子） | 不允许，且每个节点只有一个父节点 |

树可以看作 DAG 的一种特例（每个节点最多一个前驱）；DAG 则允许一个节点有多个前驱和多个后继，结构更灵活。

## 核心性质

- **拓扑排序（Topological Sort）**：DAG 一定存在至少一种拓扑排序 —— 把所有节点排成一个线性序列，使得每条边的起点都排在终点之前。这是 DAG 最重要的应用性质，常用于任务调度、依赖解析。
- **无环性可判定**：可以用 DFS 检测"回边"（back edge）来判断图中是否存在环，从而确认是否为 DAG。
- **最长路径/关键路径**：由于无环，DAG 上求最长路径、最短路径都可以通过一次拓扑排序 + 动态规划在线性时间内解决（不需要像一般图那样处理环带来的复杂度）。

## 典型应用场景

- **任务/构建依赖**：Make、Maven、Gradle 等构建工具的依赖图；CI/CD 流水线（如 GitHub Actions 的 job 依赖）。
- **任务调度系统**：Airflow、Argo Workflows 等用 DAG 描述任务之间的执行顺序和依赖关系。
- **版本控制**：Git 的提交历史本质上是一个 DAG（每个 commit 指向其父 commit，只会向前推进，不会成环）。
- **数据处理/编译**：Spark、Flink 等大数据引擎用 DAG 表示计算的执行计划（Stage/Task 之间的依赖）；编译器中的表达式求值树、SSA 中间表示。
- **区块链/分布式账本**：某些非链式结构（如 IOTA 的 Tangle）用 DAG 代替传统链式结构以提升并发写入能力。
- **知识图谱/关系建模**：表示"先修课程"、"组织层级审批链"等具有依赖但无循环的关系。

## 一个简单例子

假设一个构建任务的依赖关系：

```
A → B → D
A → C → D
```

- A 是起点，D 依赖于 B 和 C，B、C 都依赖于 A。
- 这是一个 DAG：存在方向，且不存在从 D 回到 A 的路径。
- 合法的拓扑排序之一：`A, B, C, D` 或 `A, C, B, D`。

如果反过来又加一条边 `D → A`，图就出现了环（A→B→D→A），不再是 DAG。

## 小结

DAG 是"有依赖但无循环依赖"关系的标准数学模型。只要业务场景里出现"任务 A 必须在任务 B 之前完成"这类偏序关系，且不存在互相依赖的死循环，就可以用 DAG 建模，并借助拓扑排序来确定合理的执行顺序。
