# 微服务划分规范

> 核心来源：Microsoft Azure Architecture Center《微服务体系结构设计》系列（域分析 → 战术 DDD → 识别微服务边界）。本文汇总为可执行的划分规范，供新服务拆分、存量系统重构时参考。

## 一、总原则

- **围绕业务功能划分**，而不是围绕数据访问或消息传送等水平层划分。
- **松散耦合 + 高功能内聚**：修改一个服务时无需同时修改其他服务；每个服务有单一明确的用途。
- **微服务不小于聚合，不大于限界上下文**（Bounded Context）。
- **先粗后细**：不确定时从更粗粒度的微服务开始。把一个服务拆成两个，比在多个服务间重构功能容易得多。
- 服务边界评估是**持续迭代**的过程，不是一次性设计；必要时重新定义边界。

## 二、划分方法（三步走）

### 第 1 步：领域分析（战略 DDD）

> [!tip] 实践指南
> 事件风暴的组织方式、操作步骤、产出物模板和验收清单，参见 [[领域分析（战略 DDD）实践指南]]。

1. 分析业务域，映射所有业务功能及其连接关系（事件风暴 / 白板草图均可）。
2. 识别**子域**并分类：
  - **核心子域**：有竞争优势，需详细建模和重点投入。
  - **支持子域**：维持业务运转，但不构成竞争优势。
  - **泛型子域**：行业已解决的问题，优先用现成方案（如用户账户、呼叫中心）。
3. 注意**康威定律**：系统结构会反映团队沟通结构。应主动用领域分析定义边界，再让团队所有权对齐边界，而非被动映射组织架构。
4. 识别外部系统集成点（CRM、支付、计费等），明确边界防泄漏。

### 第 2 步：定义限界上下文（Bounded Context）

- 同一实体在不同上下文中可以有**不同的模型**（例：维修预测用无人机的物理特征，派单调度只需可用性和 ETA）。
- 用**上下文映射**记录上下文间的关系模式：
  - **客户-供应商**：上游提供下游依赖的数据/服务，双方谈判契约。
  - **开放主机服务 + 已发布语言**：上游公开明确定义的接口（如 OpenAPI），下游按契约消费。
  - **防腐层（Anti-Corruption Layer）**：下游建转换层，保护自身模型免受上游模型变更影响。
  - **独立方式**：两个上下文无集成，各自独立演进。
- 对接遗留系统/外部系统时，用**防腐层**或**绞杀者模式（Strangler Fig）**强制边界。

### 第 3 步：战术 DDD 识别微服务

1. **聚合（Aggregate）是微服务的最佳候选**——它派生自业务需求、有高内聚、是持久化边界、松散耦合。
2. **领域服务（Domain Service）也是候选**——跨多个聚合的无状态操作，典型如工作流编排。
3. **验证清单**：
  - 每个服务只有一个明确职责。
  - 服务之间**无聊天式调用**（chattiness）：拆开后频繁通信，说明应合并。
  - 足够小：单个小团队可独立构建、测试、部署。
  - **无"必须一起部署"的相互依赖**。
  - 服务可独立演进、独立部署。
  - 边界避免数据一致性与完整性问题（必要时用最终一致性换取拆分收益）。

## 三、聚合设计规则（决定边界的关键）

- **设计小聚合**：只包含必须在单个事务中保持一致的数据；生命周期独立的实体各自成聚合（如 Delivery、Package、Drone、Account 各自独立）。
- **仅按 ID 引用其他聚合**：聚合内只存 `DroneId`、`PackageId`，不直接引用对象。
- **跨聚合用最终一致性**：跨聚合的业务流程用**领域事件**异步协调（如 DeliveryCompleted 触发开票）。
- 实体与值对象：实体通过唯一标识保持身份连续性，值对象通过属性表达领域概念；默认优先使用值对象，只有业务需要持续跟踪身份时才建模为实体。详细区别、判断方法与示例参见 [[DDD 中的实体与值对象]]。

## 四、粒度取舍（非功能需求驱动）

- **团队规模**：服务要小到单个团队能独立负责。
- **数据类型/技术栈**：不同部分对存储和查询需求不同，可拆分并选择各自合适的存储（Polyglot Persistence）。
- **可伸缩性**：吞吐量要求不同的部分独立扩缩。
- **可用性/容错/安全**：面向客户的服务与后端服务要求不同，可分别定义架构特性。
- 拆分常因非功能需求产生：如交付历史分析（长期存储 + 大数据查询）从实时交付服务中拆出独立服务；高吞吐入口拆出独立引入服务做负载调配。

## 五、典型反模式 / 注意事项


| 反模式    | 说明                                           |
| ------ | -------------------------------------------- |
| 服务过大   | 跨多个限界上下文混模型 → 返回领域分析重做                       |
| 服务过碎   | 聊天式调用、网络延迟、事务分散 → 合并相关功能                     |
| 贫血领域模型 | 业务逻辑全在 Service 类里，实体只传数据 → 把验证、状态转换、业务规则放回实体 |
| 共享数据库  | 多个服务直接跨库查 → 破坏自治性，应用 Feign/API 契约            |
| 忽略组织现实 | 按组织结构图而非业务域划分（康威定律被动生效）→ 主动对齐                |


## 六、与现有系统的衔接

- **绞杀者模式（Strangler Fig）**：增量重构——用新微服务逐步替换旧单体功能，边缘功能先行。
- **防腐层（ACL）**：与遗留系统对接时隔离模型差异。
- **事件驱动**：跨服务数据最终一致性用消息队列（Kafka / 服务总线）+ 领域事件/集成事件，避免分布式事务。
