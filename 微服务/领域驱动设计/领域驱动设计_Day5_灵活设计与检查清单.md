## 阅读重点（蓝皮书）

优先读：柔性设计（意图显现、副作用、断言等），并快速回顾大型结构 / 演进相关章节。带走这些话：

| 主题 | 你要带走的一句话 |
| --- | --- |
| 意图显现 | 方法名与结构应让「业务在干什么」一眼可见，而不是藏在技术过程里 |
| 副作用明确 | 会改状态的操作要显式；能做成无副作用的计算就别混进命令 |
| 断言 / 不变式 | 把「必须永远为真」写进模型（或测试），别只靠约定 |
| 独立类 / 闭包运算 | 能独立理解、能组合的小概念，比巨型过程好演进 |
| 声明式设计 | 描述「要什么结果」，少堆命令式细节 |
| 演进 | 模型随理解加深而重构；统一语言变了，代码名要跟着变 |

读的时候问自己：这段代码是在讲业务规则，还是在讲「怎么把字段写进库」？

## 核心概念（Day 5 够用）

### 1. 柔性设计（几条实用抓手）

- **意图显现**：`placeOrder` / `allocateInventory` 比 `process` / `handle` 更像统一语言。
- **副作用隔离**：查询尽量纯；改状态的命令边界清晰（常与聚合事务边界重合）。
- **不变式**：聚合内「什么永远不能坏」要可检查（创建/工厂/方法里断言）。
- **小而稳的概念**：值对象、领域服务、明确的上下文边界，让改动局部化。

### 2. 贫血模型 vs 有行为的模型

- **贫血**：实体只剩 getter/setter，规则全在 Service/Manager 的 if 里。
- **有领域味道**：关键业务不变式与决策落在实体/值对象/领域服务上，应用服务负责编排与事务。
- 不是「禁止 Service」，而是问：规则该不该跟着领域概念走？

### 3. 何时用 DDD，何时事务脚本就够

| 更适合深入建模 | 事务脚本 / 简单 CRUD 往往够用 |
| --- | --- |
| 规则多、变化快、有竞争力的核心域 | 支撑/通用、明显表单进出 |
| 多概念协作、一致性边界清晰 | 几乎无跨对象不变式 |
| 业务专家需要持续对话同一套词 | 一次性工具、内部批处理 |

### 4. 五日收束：战略 + 战术对照

- **战略**：限界上下文、映射、核心域（Day 4）
- **战术**：实体/值对象/服务、聚合/仓储（Day 2–3）
- **协作**：统一语言贯穿始终（Day 1）
- **演进**：柔性设计让模型跟得上理解（今天）

## 今日练习

### 练习 A · 用检查清单审一个真实模块

选你熟悉的一个模块（订单、工单、车辆、计费任一），逐条打勾并各写一句证据：

- [ ] 关键业务词是否在代码 / 文档 / 口头讨论中一致？
- [ ] 实体与值对象是否分清？有没有「为了落库硬加 id」？
- [ ] 聚合边界是否过小或过大？跨聚合修改是否误用同一事务硬绑？
- [ ] 仓储是否泄露 SQL / ORM 细节给领域层？
- [ ] 是否存在跨限界上下文的「万能模型 / 共享大表」？
- [ ] 核心域是否被当成普通 CRUD 对待？
- [ ] 复杂处是领域规则，还是贫血模型 + 一堆 if？

### 练习 B · 找一处「意图不显现」

指出一个方法/类名（或流程名），说明：

1. 现在名字在说什么（偏技术还是偏业务）？
2. 若按统一语言改名，会叫什么？
3. 改名后，副作用/不变式是否更容易被看见？

### 练习 C · 写一页「本团队 DDD 入门约定」

控制在一页内，至少包含：

1. **何时上聚合 / 统一语言**（例如：核心域、规则 ≥ N 条、多角色常吵词义时）
2. **何时事务脚本就够**（支撑域、简单 CRUD、一次性脚本）
3. **跨上下文默认做法**（id 引用 + 防腐/已发布语言，禁止直接共享大实体）
4. **命名约定**：代码名 = 讨论名 = 文档名；禁止 `Manager`/`Helper` 当业务词
5. **评审时必问的 3 个问题**（自拟，可参考上面检查清单）
