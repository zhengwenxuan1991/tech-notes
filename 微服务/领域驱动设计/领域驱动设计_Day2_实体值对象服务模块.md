## 今天目标

分清模型驱动设计的四块积木：

1. **实体（Entity）**：靠**连续身份**区分，属性可变，仍是「同一个东西」。
2. **值对象（Value Object）**：无身份、按属性相等、宜不可变、可整体替换。
3. **服务（Service）**：放不进实体/值对象的**领域行为**（无状态、动词感强）。
4. **模块（Module）**：用业务语言给模型分区，降低心智负担。

---

## 阅读重点（蓝皮书）

优先读：模型驱动设计相关章节——实体、值对象、服务、模块。带走这些话：

| 主题 | 你要带走的一句话 |
| --- | --- |
| 实体 | 同一性靠 id/生命周期，不靠「所有字段都一样」 |
| 值对象 | 没有独立生命周期；改了就换一个新值，不要硬加表主键当业务身份 |
| 领域服务 | 业务规则跨越多个对象、又不自然属于某一个时，用领域服务表达 |
| 模块 | 包名/命名空间应是业务分区，不是按 Controller/Util 技术层切碎领域 |

读的时候问自己：这个概念若做成「带 id 的表」，会不会把本该可替换的值，伪装成可追踪的实体？

## 核心概念（Day 2 够用）

### 1. 实体

- 有**连续身份**：哪怕地址、状态全变，仍是同一订单/同一车辆。
- 相等：比身份，不比全部属性快照。
- 例子：订单、工单、车辆、用户账号（在「身份管理」语境下）。

### 2. 值对象

- **无身份**；相等 = 属性全部相等。
- 倾向**不可变**：要改就创建新实例替换。
- 例子：金额（含币种）、邮箱地址、时间区间、车牌号（若业务不追踪「这张牌的历史」）、收货地址快照。
- 反模式：给金额表加自增 id，再到处 join——把值当成了实体。

### 3. 领域服务

- 操作的是领域概念，但**职责不属于某一个实体/值对象**。
- 无状态（或不持有业务身份）；命名用业务动词短语。
- 例子：「计价」「转账时的汇率换算策略」「根据规则分配客服」——若硬塞进某个实体会扭曲模型。
- 注意：应用服务（用例编排、事务）≠ 领域服务（业务规则本身）。今天先分清「领域里的服务」。

### 4. 模块

- 按**统一语言**里的子域/概念簇分包，而不是按技术角色。
- 好模块：打开包名就能猜业务边界；坏模块：`util`、`common`、`manager` 吞噬一切。

## 今日练习

接昨天的业务词表，做类型映射。

### 练习 A · 词表 → 类型

| 业务词 | 判为（实体/值对象/领域服务/其他） | 一句话理由 |
| --- | --- | --- |
| 例：工单 | 实体 | 有工单号，状态会变但仍是同一单 |
| 例：关单时限 | 值对象 | 一段时长/截止点，可整体替换 |
|  |  |  |

至少填满昨天词表里的名词与关键动词。

### 练习 B · 三个值对象深挖

举 **3 个**值对象（推荐：金额、地址、时间区间，或你业务里的等价物），对每个写：

1. 由哪些属性组成？
2. 为何不该做成「带 id 的表/实体」？
3. 相等规则是什么？变更时是修改字段还是替换整个对象？

### 练习 C · 找一个该用领域服务的点

找一处「规则横跨两个以上概念」的行为，写成：

- 服务名（业务动词）
- 输入/输出（用统一语言）
- 为何不适合放进某一个实体

今天结束时，你应能：

## 学习小提示

- 今天仍**不要**急着上聚合根、仓储细节（明天才是）。

- 值对象做得好，实体会变瘦，规则更清晰。
