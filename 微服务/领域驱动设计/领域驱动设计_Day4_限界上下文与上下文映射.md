## 今天目标

从「一个大模型」走向「多个有边界的模型」：

1. **限界上下文（Bounded Context）**：模型适用的明确边界；边界外换模型或翻译。
2. **上下文映射（Context Map）**：上下文之间怎么协作——防腐层、开放主机、共享内核、客户-供应商等。
3. **蒸馏与核心域**：把最能形成竞争力的部分标出来，投入最多建模精力。

## 阅读重点（蓝皮书）

优先读：限界上下文、上下文映射、蒸馏（核心域 / 支撑域 / 通用域）。带走这些话：

| 主题 | 你要带走的一句话 |
| --- | --- |
| 限界上下文 | 同一词在不同边界可以有不同含义；边界内语言必须统一 |
| 上下文映射 | 集成关系要显式画出，别假装「一张企业级万能模型」能打天下 |
| 防腐层（ACL） | 用一层翻译隔离外部模型，别让对方的词污染你的核心模型 |
| 开放主机 / 已发布语言 | 对外提供稳定协议，让多方按同一语言对接 |
| 共享内核 | 少量真正共享的模型；共享面越大，协调成本越高 |
| 客户-供应商 | 上游供应模型/接口，下游消费；权力与节奏要谈清楚 |
| 核心域 | 竞争力所在；支撑域/通用域可以买、借、简化，别平均用力 |

读的时候问自己：这个系统里「用户」「订单」是不是在不同子系统里其实不是同一个概念？

---

## 核心概念（Day 4 够用）

### 1. 限界上下文

- 一个上下文 = 一套统一语言 + 一套模型 + 明确边界。
- 边界内：词义一致、模型一致；边界外：不要直接复用同一套类/表当「真理」。
- 常见信号：同一词在销售、履约、财务里含义不同，却硬塞进一张 `User` / `Order` 表。

### 2. 上下文映射（常见关系）

| 关系 | 直觉 |
| --- | --- |
| 防腐层 | 下游用适配层吃上游脏模型，保护自己的核心语言 |
| 开放主机服务 | 上游提供稳定 API / 协议给多方 |
| 已发布语言 | 双方约定的交换格式（如标准事件 schema） |
| 共享内核 | 两边共用一小块模型与代码；慎用、要治理 |
| 客户-供应商 | 下游提需求，上游排期；有明确上下游 |
| 遵从者 | 下游完全跟上游模型走（成本低，自主性差） |
| 各行其道 | 几乎不集成，或只做极薄对接 |

### 3. 蒸馏：核心域 vs 支撑 / 通用

- **核心域**：差异化、最值得深挖建模的地方。
- **支撑域**：必要但非差异化（可简化实现）。
- **通用域**：行业通用能力（优先买/借成熟方案）。
- 战略意义：把最好的人与时间放在核心域，而不是平均 CRUD。

### 4. 「用户 / 订单」跨上下文怎么处理

- 不要一张万能表打天下。
- 各上下文保留自己的模型（如「下单客户」「履约收货人」「结算账户」），用 **id 引用 + 翻译/同步** 连接。
- 需要对外交换时，走映射关系（ACL / 已发布语言），而不是直接 import 对方实体。

## 今日练习

接前三天的词表、实体/值对象与聚合边界。

### 练习 A · 画 3–6 个限界上下文

选你熟悉的系统，画出 3–6 个上下文，每个写清：

1. **上下文名称**（用业务语言，不要用技术层名）
2. **该边界内的关键统一语言词**（5–10 个）
3. **主要聚合/用例**（各 1–2 个即可）

### 练习 B · 标集成关系

在图上用箭头标出上下文之间的关系，至少标出：

- 1 处**防腐层**或「本该有防腐却没有」的气味
- 1 处**客户-供应商**或**开放主机**
- （可选）1 处共享内核是否合理

### 练习 C · 标出核心域

写出：

1. 哪个上下文是**核心域**？为什么（一句话竞争力）？
2. 哪个更像支撑域 / 通用域？若继续深挖建模，机会成本是什么？

### 练习 D · 一词多义

举「用户」或「订单」（或你业务里的同名词），说明：

- 在上下文 A 的含义
- 在上下文 B 的含义
- 若强行一张表，会出什么错？更合理的拆法是什么？
