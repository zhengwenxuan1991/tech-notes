## 今天目标

理解「一致性边界」和「怎么取存模型」：

1. **聚合（Aggregate）**：一组对象的一致性边界；对外只通过**聚合根**访问。
2. **工厂（Factory）**：负责创建复杂聚合，保证一出生就合法。
3. **仓储（Repository）**：用领域方式获取/保存聚合（像集合，不是 SQL/DAO 细节）。
4. **生命周期**：创建 → 存取 → 删除/归档；谁负责哪一段。

## 核心概念（Day 3 够用）

### 1. 聚合与一致性边界

- 聚合 = **必须一起保持正确**的一组对象。
- 边界内：同一次事务里保证不变量（如「订单金额 = 行项目之和」）。
- 边界外：只持有其他聚合的**身份引用**，不要直接持有内部对象指针乱改。
- 常见反模式：一个巨型聚合（整库一张图）或过碎的聚合（处处跨事务硬绑）。

### 2. 聚合根

- 根是外界的**唯一入口**；子实体/值对象通过根暴露的行为修改。
- 例子：`Order` 是根，`OrderLine` 在边界内；外面不该直接 `line.setQty(...)` 绕过根。
- 「为什么不能随意在 Order 里深层乱改」：绕过根 = 绕过不变量检查。

### 3. 工厂

- 当创建步骤多、不变式复杂时，用工厂（或工厂方法）组装合法聚合。
- 工厂保证：**创建出来就能用**，而不是半成品再慢慢补丁。

### 4. 仓储

- 接口像「按身份找聚合 / 保存聚合」的集合，而不是 `OrderDao.selectJoinLine...`。
- 领域层依赖仓储抽象；实现层（ORM/SQL）藏在基础设施。
- 只给需要独立存取的**聚合根**配仓储，不要每个表一个 Repository。

### 5. 生命周期（简化）

| 阶段 | 谁出手 |
| --- | --- |
| 创建 | 工厂 / 聚合根上的创建行为 |
| 重建与查询 | 仓储（按 id / 规格） |
| 变更 | 通过根上的领域行为 |
| 持久化 | 仓储 save（事务边界通常对齐一次用例对一个主聚合的修改） |
| 删除/归档 | 按业务规则；注意别误删仍被引用的根 |

## 今日练习

接前两天的业务词表与实体/值对象映射。

### 练习 A · 画 1–2 个聚合

选你熟悉的业务（订单 / 工单 / 车辆等），对每个聚合写清：

1. **聚合根**是谁？
2. **边界内**有哪些实体/值对象？
3. **哪些改动必须同事务**（不变量列表，至少 2 条）？
4. **哪些只能通过根访问**（列出禁止的「直接改子对象」路径）？

可用简图：`根 —— 子实体/值对象`，边界外用 `→ 其他根(id)`。

### 练习 B · 仓储接口草稿

为其中一个聚合根写 3–5 个仓储方法名（领域语言），例如：

- `findById`
- `save`
- 1–2 个业务查询（用规格/查询对象表达意图，避免泄露 SQL）

并写一句：为何领域层不该直接依赖某张表的 DAO。

### 练习 C · 跨聚合场景

举一个「看起来想一个事务改两个根」的例子，说明：

- 若硬绑同一事务，风险是什么？
- 更合理的边界/协作方式是什么（最终一致、领域事件、应用服务编排等，选你能说清的一种即可）？
