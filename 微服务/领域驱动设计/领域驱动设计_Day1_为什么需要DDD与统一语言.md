## 今天目标

明白两件事：

1. **复杂在哪**：多数系统难维护，根因常在业务理解与表达，而不只在框架/性能。
2. **模型是什么**：模型是对业务的**有选择的抽象**，用来支撑讨论、设计和代码，而不是把现实逐条抄进数据库。

## 核心概念（Day 1 够用）

### 1. 领域（Domain）

软件要服务的那块业务世界。例：订单履约、车辆监管、客服工单。

### 2. 模型（Model）

对领域的抽象：留下对解决问题有用的概念与关系，刻意丢掉无关细节。好模型能让人**用业务话**讲清系统在干什么。

### 3. 统一语言

- 业务说「关单」，代码里却写 `closeTicket` / `finish` / `archive` 混用 → 语言不统一。
- 目标：讨论怎么说，类/方法/字段就怎么命名；文档也用同一词。
- 发现「同一个词两种意思」或「两个词同一意思」→ 立刻对齐，并改代码/文档。

### 4. 为什么需要 DDD（入门版）

当业务规则多、概念易混、多人长期改同一套系统时，纯 CRUD + 技术分层往往撑不住。DDD 先保证：**大家在谈同一套业务概念**，再谈聚合、限界上下文等（后面几天学）。

## 今日练习

选一个你熟的业务（订单 / 车辆监管 / 客服工单等），完成下面三步。

### 练习 A · 业务词表

列出 10–20 个业务里真正会被讨论的词（名词 + 关键动词）：

| 业务词 | 一句话定义（用业务说法） | 出现场景 |
| --- | --- | --- |
| 例：关单 | 工单处理结束，不再受理跟进 | 客服结案 |
|  |  |  |
|  |  |  |

### 练习 B · 语言裂缝

标出「开发说法 ≠ 业务说法」的词：

| 业务怎么说 | 代码/接口现在怎么说 | 问题（歧义 / 两个词一事 / 技术词冒充业务） | 建议统一成 |
| --- | --- | --- | --- |
|  |  |  |  |
|  |  |  |  |

### 练习 C · 一句话问题陈述

用**纯业务语言**写 3–5 句：这个系统到底解决什么问题？为谁？成功长什么样？

（不要出现：微服务、表结构、MQ、框架名。）
