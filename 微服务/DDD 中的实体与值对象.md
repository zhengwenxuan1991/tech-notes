# DDD 中的实体与值对象

在领域驱动设计（DDD）中，实体（Entity）和值对象（Value Object）都是领域模型的基本构件。两者最核心的区别是：

> [!abstract] 核心判断
> **实体关注“它是谁”，值对象关注“它是什么”。**

## 一、实体（Entity）

实体具有领域需要持续识别的唯一身份。即使它的属性发生变化，只要身份没有改变，它仍然是同一个对象。

例如，一个订单的状态、收货地址可以发生变化，但只要 `OrderId` 不变，它仍然是原来的订单。

```java
class Order {
    private OrderId id;
    private OrderStatus status;
    private Address shippingAddress;
}
```

实体通常具有以下特征：

- 具有稳定的唯一标识，如订单 ID、用户 ID、车辆 ID；
- 拥有需要业务持续跟踪的生命周期；
- 状态可以随业务过程发生变化；
- 通过身份标识，而不是全部属性，判断是否为同一个对象；
- 通常承担与自身状态相关的业务行为和业务规则。

常见实体包括用户、订单、合同、车辆和银行账户。两个用户即使姓名、年龄完全相同，只要用户 ID 不同，就是两个不同的实体。

## 二、值对象（Value Object）

值对象没有领域需要关注的独立身份，而是通过一组属性共同表达某个领域概念。

例如，地址由省、市、详细地址等属性共同描述。当两个地址的全部有效属性相同时，在多数业务场景中可以认为它们相等，无需为每个地址分配领域身份。

```java
class Address {
    private final String province;
    private final String city;
    private final String detail;
}
```

值对象通常具有以下特征：

- 不依赖唯一 ID；
- 通过全部有效属性判断是否相等；
- 没有独立的业务生命周期，通常依附于实体或聚合存在；
- 应优先设计为不可变对象；
- 发生变化时创建新对象并整体替换，而不是原地修改。

常见值对象包括金额、地址、日期范围、坐标、颜色和手机号。

```java
class Money {
    private final BigDecimal amount;
    private final Currency currency;

    public Money add(Money other) {
        // 校验币种一致后，返回一个新的 Money
        return new Money(amount.add(other.amount), currency);
    }
}
```

`Money` 不能只比较数值，`100 元`和`100 美元`是两个不同的值。将金额和币种封装为值对象，也能集中维护精度、币种匹配、负数限制等业务规则。

## 三、实体与值对象的区别

| 对比维度 | 实体 Entity | 值对象 Value Object |
| --- | --- | --- |
| 核心关注点 | 身份 | 属性值 |
| 领域身份 | 有 | 无 |
| 相等判断 | 唯一标识是否相同 | 全部有效属性是否相同 |
| 生命周期 | 有独立生命周期 | 通常依附于实体或聚合 |
| 状态变化 | 可以持续变化 | 推荐不可变，变化时整体替换 |
| 常见例子 | 用户、订单、车辆 | 金额、地址、时间范围 |

例如，“张三修改了手机号”之后仍然是同一个用户，因为其用户 ID 没有变化，所以用户是实体。

而“订单的收货地址从地址 A 修改为地址 B”，更适合理解为订单使用新的地址值替换旧的地址值，而不是地址 A 自身变成了地址 B，所以地址通常建模为值对象。

## 四、两者的关系

实体和值对象不是互斥、孤立的概念，它们通常共同组成实体或聚合：

```text
订单实体
├── 订单 ID：值对象
├── 订单状态：值对象或枚举
├── 收货地址：值对象
├── 商品明细：实体或值对象
└── 总金额：值对象
```

实体承载业务身份和生命周期，值对象负责准确表达实体中的属性、度量和业务规则。使用值对象还能减少基础类型滥用，让模型具有更明确的领域语义。

例如，相比下面的方法：

```java
void pay(BigDecimal amount, String currency)
```

使用领域类型更清晰：

```java
void pay(Money money)
```

## 五、如何判断

判断一个领域对象是否应建模为实体，可以询问：

1. 业务是否需要区分两个属性完全相同的对象？
2. 属性变化后，业务是否仍认为它是原来的对象？
3. 是否需要长期跟踪它的生命周期？
4. 其他对象是否会通过 ID 引用它？

如果多数答案为“是”，通常应建模为实体。

判断一个领域对象是否应建模为值对象，可以询问：

1. 它是否只用于描述一个值或领域概念？
2. 属性全部相同是否就可以认为对象相同？
3. 发生变化时是否可以整体替换？
4. 是否不需要单独跟踪其生命周期？

如果多数答案为“是”，通常应建模为值对象。

> [!warning] 由领域语境决定，而不是由数据库决定
> 数据库为了存储方便给值对象增加技术主键，并不会让它自动成为领域实体。判断依据是业务是否关注它的身份。

同一个概念在不同领域语境中也可能采用不同建模方式：

- 普通电商中的地址通常是值对象；地址管理系统中的地址如果需要独立审核和跟踪，则可能是实体。
- 订单项只描述商品、数量和单价时可以是值对象；如果需要单独退款、售后和状态跟踪，则可能是实体。

## 六、建模建议

- 默认优先考虑值对象，只有业务需要持续跟踪身份时才建模为实体。
- 实体的标识必须稳定，不应使用容易变化的业务属性代替身份。
- 值对象应保持不可变，并在构造时保证自身始终有效。
- 将校验、计算和状态变更规则封装在实体或值对象内部，避免领域模型退化为只有字段的贫血模型。
- 是否为实体和值对象应结合限界上下文判断，不能脱离具体业务语境统一定性。
